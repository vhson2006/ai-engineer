# 0025. Many client sites: a Keycloak realm per site for customers, one admin realm, shared databases with `site_id`

- **Status:** Accepted, partly implemented (interim content access: ADR 0028)
- **Date:** 2026-11-10
- **Related:** 0002 (one realm → several issuers), 0003, 0004 (more than one public realm),
  0010, 0019 (the admin site becomes shared by every site), 0026, 0027

## Context

The system will serve several small businesses, each with its own site and domain (nails-web,
wine-web, laundry-web, ...). On every site, customers sign in to follow their orders and
bookings. Each business has admins who manage only their own site's posts, products, orders,
customers and marketing, through ONE shared admin site. Today there is one realm
(`nest-microservice`) for one site, and no data carries a site.

Constraints:

- A realm has one Frontend URL. Customers of one business should sign in on that business's
  domain (`auth.<site domain>`), with its look and its emails, not on a domain they don't know.
- The businesses are unrelated: a customer of one must not be signed in to another, and the same
  email on two sites is two independent accounts. A business that leaves must be removable or
  exportable on its own.
- Running one database per site multiplies migrations, connection pools and the cost of the
  managed Postgres (one 1 GB instance in the prod plan).

## Decision

1. **Keycloak: one realm per site for customers**, each with its own Frontend URL
   (`auth.<site domain>`), login theme, SMTP and password policy. Created from one template by a
   script, never by hand.
2. **One admin realm for every admin** of every site. Sign-in keeps ADR 0019's rules (password +
   OTP, non-admins refused, role re-checked by the app, short sessions). An admin's sites come
   from a membership (Keycloak Organizations or groups) emitted as a token claim. The owner of the
   system is a super admin of every site. The realms, roles and claims are listed in a follow-up
   ADR.
3. **Data: no database per site.** Each service keeps its own database (as today); every
   business table has a `site_id`, and every query filters on it. Postgres Row-Level Security may
   be added as a second lock.
4. **`site_id` never comes from the browser.** For a customer it is derived from the realm that
   issued the token; for an admin it comes from the request and must be one of the sites in the
   token's claim. Each site's web server also has its own `SITE_ID` and only asks for its site.
5. **Tokens are still verified twice (0002), now against several issuers.** KrakenD endpoints for
   customers exist once per site realm, generated by the template from a list of sites; admin
   endpoints validate against the admin realm. The services' `AuthGuard` accepts only issuers on
   a configured allow-list and maps each one to its site.
6. The sample sites (nails-web, wine-web, ...) become BFFs like portfolio-web (ADRs 0003, 0010)
   when they get sign-in or data from the API.

## Consequences

- Each business gets its own sign-in domain, accounts, look and emails; a business is removed or
  exported by removing or exporting one realm and its `site_id` rows.
- A new site = a realm from the template + a row in the site list (KrakenD, services, web app
  `SITE_ID`), all in one change. Missing one of them must fail a check, not a customer.
- Forgetting `site_id` in a query leaks data between businesses: every repository method takes a
  site, tests cover cross-site access, and RLS is the backstop.
- Keycloak runs comfortably with tens of realms. With hundreds, move customers to one realm with
  Organizations (a new ADR).
- More public realms (0004 allowed one): each needs brute-force detection and the same edge
  limits. `master` and the admin console stay private.
- Moving the existing realm `nest-microservice` (portfolio-web, admin-web) to this model needs a
  migration plan; until then it keeps working as it is.

## Alternatives considered

- **One realm for every customer of every site**: simpler (one issuer), but one sign-in domain for
  unrelated businesses, cross-site SSO and shared accounts. Kept only as the fallback above.
- **One realm per site for admins too**: an owner managing several sites would need several
  accounts and OTPs; the shared admin site would need one client per realm.
- **A database (or schema) per site**: strongest isolation, but N× migrations, pools and cost for
  small businesses. A site that needs it later can be moved out thanks to `site_id`.
- **`site_id` sent by the browser or chosen from the host header alone**: forgeable. Rejected.
